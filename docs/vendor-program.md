# Vendor equipment and sponsorship program

Decision baseline: 2026-10-07. **No vendor participation, CAD redistribution permission or signed performance-data license is established by this document.** Product pages and downloadable BIM files are leads only. Generic, detailed studio-original equipment is the complete non-sponsored game path; see [BIM/asset pipeline](bim-and-asset-pipeline.md), [product specification](product-specification.md) and [equipment/vendor implementation plan](superpowers/plans/01-equipment-bim.md).

## Independence and product truth

A vendor may license a specific SKU's dimensions, approved appearance, controls, connector definitions, operating data and logo, with distinct rights for each. Sponsorship buys disclosed placement/branding/showcase content, never a solver coefficient, scoring preference, hidden yield multiplier, exclusive progress gate or mandatory account/online dependency. A licensed SKU can physically differ from another product if versioned, condition-specific approved data supports that difference; **not all branded equipment is merely cosmetic**. Display the SKU, provenance, operating domain and uncertainty without describing game models as certified field predictions. Vendor-funded showcase scenarios visibly identify funding and use the same simulation and fairness rules. No real manufacturer name, product rendering or logo in shipped content/marketing until specifically approved; trademark/title clearance is a separate release gate.

Neutral `equipment_type_id` and product/model calibration version own physical simulation semantics. Game `instance_id`, layout, owner, ports, accumulated wear and usage remain stable through optional cosmetic substitution. Optional SKU key, asset pack hash and sponsor presentation ID are separate references, never game machine identity or sole save-load dependencies. Installation evidence in upstream identity maps is not inferred from a purchase or brand selection. Every starting equipment family has an approved, distributable original generic fallback and disclosed illustrative performance.

## Intake, approval and pilot

1. Log a candidate request internally with rights-holder contact, exact SKU/configuration/region/revision, official reference URL, proposed game use and required fidelity axes: geometry, motion/interaction, operating data, and model validity. Check whether downloadable asset rights belong to manufacturer, marketplace or separate model creator; do not represent published limits as unconditional structural/installation clearance.
2. Negotiate written grants separately for model/source access, modification/optimization and derivative rights, worldwide/territory/platform storefront distribution, marketing/screenshots, brand/trademark use, data table/photometric use, packaged save/replay persistence, future builds and expiry/withdrawal remedies. State whether existing users may retain licensed calibrated data and cached cooked pack after expiry; ask for territory/age/content restrictions and notice/attribution. Vendor must authorize source handoff and approved source hashes; confidentiality of source CAD is independent of shipped derivative permission. Counsel approves license and privacy/brand language before build access.
3. Record a machine-readable license manifest: neutral type, optional SKU/version, exact source SHA-256, rights holder, agreement/approval ID and approval-document SHA-256, approver and UTC decision, allowed uses/artifact classes, territories/platforms, duration/expiry, distribution/marketing/screenshot permission, data and logo scope, required notices, withdrawal/retention and perpetual-save clauses. Keep signed approval originals and restricted source masters in separate, audited S3-compatible storage with per-vendor isolation and role-based access; only approved redistributable source art and cooked assets enter Git LFS. No raw vendor CAD or private approval document ships. Signed approval document existence and hash must be checked by trusted build policy, not trusted because a contributor typed `approved: true` into JSON.
4. Run a **single limited SKU pilot** only after agreement: compare physical dimensions/pivots/ports and service clearance against approved drawings; obtain explicit condition-specific performance/photometric tables and operating ranges; independently review converted visual model/collision and attribution; inspect output package for source leakage. RFA conversion requires an authorized Revit export or vendor-provided IFC/mesh, never direct Bonsai RFA import. Gate model validity as separate from geometry beauty. Where a required claim lacks licensed data, retain generic illustrative equipment instead of inventing vendor calibration.
5. Approver signs exact candidate manifest hash, source digest, operating table/version, platform set and intended public visuals. Rights compiler fails closed on absent/expired/mismatched approval, disallowed region/platform/use or missing required notice. QA compares SKU and generic progression under the same scenario and confirms supplier funding is absent from equations; real approved operating distinctions may remain. Record release ledger: pack hash, executable/engine version, license grant/expiry, notices, screenshots and store territories. Publish no endorsement claim beyond agreement.

## Release, revocation and old saves

At agreement expiry or withdrawal, stop **new** distribution and marketing uses not licensed; remove prohibited logo/visuals from the next build, disable restricted pack availability and replace visuals with original generic presentation preserving envelope/pivots/ports and player ownership. Remove stored restricted masters and distribution caches according to agreement and documented retention/legal-hold policy; keep nonrestricted audit facts. Do not pretend store recall, existing installations or backups can be retroactively modified without the actual agreement/platform mechanism. Sponsor asset failure never blocks a generic-only core release.

If license permits perpetual existing-save use of a versioned performance table, pin that table/hash for existing saves while preventing unauthorized new use; the simulator still uses neutral algorithms. If performance data **must** be withdrawn, implement a versioned migration to a licensed/generic operating definition, disclose changed-model consequences and preserve original save bytes where lawful; do not claim bit-identical physics after migration. If retention itself is prohibited, surface the legal constraint and give the user a lawful migration/export path before removal when possible. Missing optional render pack loads generic mesh without deleting connections, historical crop/energy or financial records; missing mandatory performance pack must produce an explicit incompatible-pack/migration decision, never silently substitute and call replay deterministic. Forward migration writes a separate save, keeping the sole old copy intact subject to legal obligations. Verify offline load on Windows, Linux and Mac and at least one pre-withdrawal save with brand present/absent plus one data-withdrawal case before approving rollout.

Vendor access cannot gate ability to finish First Shipment, room expansion or core game modes. Maintain a funded original-art and illustrative-data baseline independent of partner response; rights uncertainty blocks only the affected licensed addition. Future candidate list is not a partnership announcement.
