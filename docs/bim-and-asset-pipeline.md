# BIM and asset pipeline

Decision baseline: 2026-10-07. B01's original First Shipment facility/MEP profile is now implemented upstream and [pinned as GrowBIM 0.2.0](../dependencies/upstream/README.md); the remaining game-pack, visual asset and vendor pipeline is planned work. The [product specification](product-specification.md), [architecture](architecture.md) and [equipment plan](superpowers/plans/01-equipment-bim.md) are binding companion contracts. Accepted upstream artifacts, not this document or a game pack, remain the source of engineering provenance. No pipeline output is professional engineering approval.

## Authority and present upstream limits

- Existing OpenCEA `program.json` is schema **0.1**; accepted design-envelope `manifest.json`, `catalog.json` and `identity-map.json` are schema **0.2** (JSON Schema 2020-12). Individual catalog product rows in the existing fixture are schema **0.1**, despite their 0.2 catalog envelope. Do not invent a 0.2 product-row contract or copy upstream schemas into this repository. Canonical design artifacts are `model.ifc`, `identity-map.json`, `catalog.json`, accompanied by accepted program/revision metadata; identity `model_sha256` binds exact IFC bytes. `opencea.identity.validate_identity_map(identity, catalog, program)` validates semantic relationships without proving installed equipment, measured performance or design safety. Proposed elements cannot carry installed `asset_id`; installed assets need reported element evidence, consistent catalog product and unique attachment. `source` is provenance, `reported` is not `verified`.
- Available `growbim.ifc` operations are `build_fixture(kind, project_id, source_id, *, length_unit="m")`, `fixture_expectations(kind)`, `validate_candidate(artifacts, program)`, `build_reference_room(program, room_source_id, rack_source_id, *, scenario_source_id=None)`, `resize_reference_room(artifacts, *, length_m, depth_m, height_m, program=None)`, `move_reference_rack(artifacts, *, x_m, y_m, rotation_degrees)`, `reference_access(artifacts)`, `reconcile_placement_edit(artifacts, edited_ifc, program, element_id)` and lower-level `resize_element`, `move_element`, `rename_element`, `copy_element`, `install_element`, `replace_element`, `retire_element`. These produce candidates, not acceptance. The current `grownetics-design` bridge offers `create-demo`, `import`, `inspect`, `propose`, `reconcile-ifc`, `accept`, `export`, `validate-run`; neither that CLI nor GrowBIM offers a general IFC room/duct builder or generalized Bonsai reconciliation CLI. Preserve its export/acceptance boundary, not a direct Unreal linkage to Python internals.
- Legacy `reconcile_placement_edit` remains **selected-rack placement only**: UUID/GlobalId-bound IFC4/metre rigid 0°/90° zero-elevation movement, rejecting unrelated geometry/topology/material/identity/unit/access changes. GrowBIM 0.2.0 additionally provides `build_facility(program, source_id)` and `reconcile_facility_edit(artifacts, edited_ifc, program, element_id)` for the original 216 m² one-storey rectangular profile and selected MEP host/connected-port placement. Its native validation and reviewed acceptance check actual enclosure, floor-level doors, service clearances, typed `IfcDistributionPort` connections and system membership. General construction and new profiles still require separately versioned upstream implementation/qualification; grouping alone is not connectivity or equipment performance.
- Accepted revisions are immutable SHA-256 snapshots with expected-revision compare-and-swap and request-ID replay/conflict handling. Game construction is a distinct campaign transaction and may be exported as a candidate; neither placement nor export advances accepted HEAD. Only explicit upstream review and acceptance does. Preserve the old source digest/history when a campaign branches or accepts a new source revision.
- Upstream reference Metro MQ-2448G-80-M4 rack catalog describes approximately 1.2652375 × 0.6683375 × 2.0145375 m, converted from dimensions rounded to 1/16 inch, with four open-grid shelves and bumpers; its IFC geometry is a box envelope. It provides neither detailed game mesh nor evidence of cultivation suitability, caster clearance or unconditional safe load. Reference-room light, irrigation, environment and sensors are conceptual objects with unknown operating data. Do not elevate them to calibrated catalog entries.

Existing exchange evidence is only a synthetic IFC4/metre room and rack move in Blender **5.2.2 LTS**, Bonsai **0.8.5**, IfcOpenShell **0.8.5**, with independent web-ifc **0.0.78** reading and scripted Bonsai operations. It does not establish general GUI editing, arbitrary IFC versions or MEP round trips. GrowBIM local project/job stores use POSIX `fcntl.flock`; native Windows authoring must use a supported service host or a newly qualified upstream cross-platform locking backend, not suppress ImportError. Windows *gameplay* never starts the local authoring store.

## The four records and identifiers

1. **Accepted source:** retain exact original IFC, program, identity map, catalog, source hashes, immutable accepted revision, evidence and claims as delivered.
2. **Compiled definition:** disposable versioned semantic FlatBuffers pack plus separately cooked Unreal render variants and a manifest of source/tool/rights/model hashes. Recompile without silently revising source authority. Unsupported source/profile/units fail compilation with diagnostic identity and path.
3. **Campaign state:** game-owned world placements, connectivity, construction, equipment state and ownership, never represented as upstream reported installation. Stable typed 128-bit project/source-element/product-type/room/zone/connector/instance IDs; persist source element UUID ↔ IFC GlobalId crosswalk. Allocate each new game `instance_id` from campaign namespace and authoritative monotonic counter, including copies; never reuse an upstream installed `asset_id`. A saved functional role survives replacement only through explicit replacement command and identity mapping.
4. **Export candidate:** serialize campaign design intent, source binding, generated candidate IDs, IFC plus identity/catalog changes and a machine-readable before/after diff for review. Where upstream profile cannot express an edit, mark export blocked with named reason; do not emit a falsely accepted IFC. Upstream review can reconcile and accept a revision; the campaign retains its historical binding until an explicit user migration.

After parsing source units and composed placements, the canonical semantic frame is right-handed Z-up **metres**; Unreal is left-handed Z-up centimetres. Use `(x_ue,y_ue,z_ue)=100*(x_source,-y_source,z_source)`. Reverse triangle winding for the reflection, normalize inverse-transpose normals and update tangent handedness; collision, pivots and ports use the same transform. The triangle `(0,0,0),(1,0,0),(0,1,0)` with +Z normal maps to `(0,0,0),(100,0,0),(0,-100,0)` with reversed order and +Z outward normal. A one-metre offset must be 100 cm. Test asymmetric/nested placements and inverse round trips. Semantic packs remain SI, not Unreal units. Standard GLB is right-handed Y-up metres; record exporter/importer basis stages and convert exactly once, never bake UE centimetres/reflection into a GLB and then repeat conversion in the importer. Existing IFC4/metre fixtures do not imply all IFC uses metres: honor `IfcUnitAssignment`, reject unknown coordinate/unit systems and qualify m/mm/ft inputs explicitly.

Building storeys own gross floor polygons; rack tiers are equipment/canopy surfaces inside a storey and never multiply gross floor area. Record site/building footprints and room/support/circulation/mechanical/canopy areas separately; the first level is 18 × 12 m, 216 m² one-storey gross floor area. A duct crosses named room boundaries through typed system connections, not merely overlapping meshes. Source/project and catalog identity persist independently of mesh/material/brand changes.

## Data admission and physical fidelity

Separate **physical envelope and operating model**, **simple gameplay collision/navigation**, and **presentation mesh/material/motion**. A BIM LOD designation is not a game rendering LOD. The physical record defines documented dimensions, mount/pivot, swept volume, static/dynamic clearance, service access, usable canopy surfaces, controls, curves with valid ranges and uncertainty, and source/rights provenance per parameter. Collision uses inexpensive, conservative primitives and actor-interaction targets at reachable surfaces; visual LODs/UVs/materials/animations may be detailed without changing load, ports or walkability. Never use IFC reference boxes as shippable hero meshes or imply an attractive manufacturer mesh certifies performance.

First author detailed **original generic** rolling benches, stationary/movable racks, ducted fan/filter, cooling/dehumidification, luminaires, fertigation/reservoir/pump, sensors, cart and processing station. Exposed rails, wheels/bearings, handles, grilles, flanges, housings, fasteners, service doors and believable surface finishes must read at first-person 1.5 m range; no copied protected vendor geometry, logos or photos. Two starter bench/rack configurations, two lights and connected shared plant must support the First Shipment loop without a vendor pack. Generic operating parameters are labeled illustrative game balance, not sourced engineering claims. Later approved SKU data may distinguish real capacities/curves legitimately; sponsorship is never a solver input and a brand swap never grants a hidden advantage.

- Rolling benches: travel follows authored rails/end stops. Reserve the full **swept envelope** during motion; prevent movement through workers/carts/equipment and preserve protected egress/service routes. The selected working aisle can shift as benches move; do not require all bench aisles open simultaneously, which would defeat a genuine rolling-bench system. Check accessible controls and safe worker/cart relocation before motion, with explicit job blockage when a nonselected aisle is closed. Rack tiers/canopy remain inside real building storeys, with separate equipment loads and ceiling limits.
- Air: fan is coupled to pressure–flow curve across operating speed/duct/filter resistance, not a single maximum-cfm headline. Blocked filter shifts the operating point and alters sensible/latent/CO₂ consequences. Typed supply/return duct ports carry direction, section/connector size, flow units, pressure constraints and failure states; routing must reject incompatible joins and inaccessible service panels.
- Light: track electrical input watts **separately** from photon flux/distribution (e.g. µmol/s and canopy PPFD µmol/m²/s), variant spectrum and dimming maps. Watts drive electrical/heat loads while photon exposure drives crop response; fixture brightness is not a PPFD meter. Unknown photometrics remain disclosed approximations, not converted from marketing lumens without calibration.
- Cooling/dehumidification: condensate removal depends on inlet temperature, humidity and flow/operating mode. Map at least two documented conditions for any SKU whose claims are used; do not apply nominal pints/day to every state. Condensate drain requires compatible gravity/pump path and capacity; blocked/disconnected drain reduces operation or faults. MEP electrical ports declare voltage/phase/power/circuit capacity and protective assumptions; water feed, dosing and return/drain ports declare compatible medium/direction/flow. Commission only on complete capacity-checked topology, safe reach and maintenance envelope; show exact missing/mismatched port or capacity reason. These are gameplay engineering checks, not compliance certificates.

Proposed source-admission targets: SKU footprint/pivot within max(2 cm, 1% documented dimension), connector centres within 2 cm/5° of approved drawings unless tighter source tolerances apply. This is **source-model fidelity**, distinct from compiler fidelity: an admitted model must cook without moving fixed interfaces/end-stops more than 10 mm or visible architectural edges more than 25 mm. Preserve the source's known uncertainty; conversion must not use it to excuse additional error. Initial visual budgets: hero fan/rack/dehumidifier ≤40k/8k LOD0/1 triangles; repeated bench module/light ≤12k/2k; ≤12 simple collision hulls; repeats ≤2 material slots/one 2048² atlas, heroes ≤4/two 2048². Exceptions require measured platform review. Source IFC/raw CAD never enters runtime imports.

## Offline authoring, reproducibility and release

1. Intake accepted artifacts and only approved original/generic or licensed masters. Verify SHA-256, exact upstream envelope/item versions, source revision, catalog/identity references and authorization scope before processing. Unknown rights = reference-only quarantine, **not** asset-pack compilation. Public download or BIMObject/BIMsmith design-use terms do not permit game redistribution by implication.
2. On a separate supported creator host, validate IFC/project identity and extract semantic placements/relationships with pinned Python 3.12, GrowBIM/OpenCEA and optional IfcOpenShell. Isolate Blender/Bonsai authoring from runtime; save .ifc and .blend separately, IFC as semantic exchange and GLB plus versioned semantic sidecar as default geometry exchange. STEP/DWG need approved conversion rights/tools; **RFA requires vendor-provided IFC/mesh or authorized Revit-based export**, not supposed direct Bonsai import. Preserve GUIDs, placements, ports and parameter units through sidecar and crosswalk. Treat Datasmith as optional offline acceleration only after platform qualification; no engine plugin is a runtime BIM parser.
3. Author original mechanics, pivots, rail animation, UV/PBR, game LODs and simple collision; inspect visual silhouette against physical envelope and service clearances. Compile source-hash-keyed semantic pack and platform render pack using pinned scripts/toolchain settings. `license-manifest` records source hash, rights holder, written approval ID and **SHA-256 of approval artifact**, allowed modification/derivative/distribution/marketing/territory/platform/duration, data/brand scope, expiration/withdrawal rule and notice obligations. The compiler fails closed for missing, mismatched, expired, wrong-platform or restricted approval; generic original studio work still has explicit owned-source approval entries.
4. Stage approved distributable original masters in `content/approved-sources/` and approved game content in `game/Content/` via Git LFS. Restricted source vendor CAD, confidential facility designs and signed approval originals live only in separate access-controlled S3-compatible object storage; isolate per sponsor, log access, encrypt/retain per agreement, keep secrets off source control and untrusted CI. Build workers get short-lived minimum-scope access only after approval; no raw CAD, confidential textures, RFA, IFC source or secret in a public game pak. Immutable content-addressed derived records retain full provenance in the private release ledger.
5. Cooker emits deterministic catalog keys and reproducible pack hashes from pinned source bytes, generator/settings, schemas, rights revision and engine version; compare two clean controlled cooks' semantic output and cooked-content inventories/hashes under identical platform/toolchain (exclude documented nonsemantic timestamps). Trusted Windows/Linux/Mac runners inspect packages for forbidden sources and approvals; verify install/load, collision and port alignment, optional unlicensed/generic-only build, platform-specific visual fallback and dependency notices. Unreal **5.8.3** is the baseline; cook regression is required for any engine patch. No sponsor asset or permission can block generic core shipment.

Default GLB tooling and optional CAD accelerators still need explicit license/toolchain review. Renderer-specific options, including Nanite, hardware RT and vendor upscalers, cannot be mandatory on Mac; cooked fallback LOD/raster variants must be present. Game construction stays offline on all target OSes without Blender, Bonsai, IFC parsing or GrowBIM local store.
